# 角色宣言编辑：验证与导入

本次角色表单编辑没有应用，原面板保留。原失败调用只记录
`EDIT_RESULT_SPEC` 和 `$.patch`，没有具体底层字段，且没有保存被拒绝的正文。
因此不能确定原回复是哪个属性不合法，不能将后续夹具复现当作原故障原因。
原调用回执和诊断保持不变，没有自动重试或再次调用模型。

已收紧 Spec 0.7 的 Codex 编辑传输：CodexEditDraft 0.2 的 `add-input-row`
只填写输入属性与目录配方，程序产生匹配的控件/状态 ID、绑定、事件和标准校验提示。
当前 dispatch 为 0.3，保留该新增输入形状，并增加独立无需修改结果，见 [局部编辑协议](panel-editing.md)。
`validationMessages:null` 表示使用标准提示；自定义提示仍须显式给出两个非空单行字符串。
现有输入属性和 `submit.fields` 仍显式填写，不推测提交范围。
生成的公共 Patch/EditProposal 和 Spec 版本不变，旧草稿 0.1 继续接受原形状。
任何不合法的值仍终止整批修改，不修补或截断输入。

诊断现在可保存一层 `cause:{validatorCode,path}`，仅白名单代码和协议路径。
例如空校验提示会明确指出 `validation.requiredMessage`，不暴露原值或错误消息。
旧诊断没有底层信息时仍按旧协议读取，不伪造或补写。

针对这次完整需求，另外产生并通过公共校验与资源编译的 **新 Agent 夹具方案** 在：

- `output/role-declaration-edit-proposal-v1/edit-proposal.json`
- `output/role-declaration-edit-preview-v1/panel.bundle.json`

它不是原 Codex 回复，也不是模型成功回执。整批包含三个操作：角色名上限变为 16、
占位文字改为“给角色起个名字”；角色名后增加可选宣言，初值空、上限 30；
确认同时提交角色名和宣言。取消及其它属性保留。

当前失败页面的面板和修改描述没有变化时，可以直接打开“面板操作”→“高级工具”，
在“接收修改方案”中使用“导入修改方案”，选上述 `edit-proposal.json`。
该导入不调用模型，应用时保留当前角色名，整批可以撤销。
若修改上下文已丢失，使用相同原面板和完整原修改描述，点“仅准备修改上下文”后再导入。
不能将该方案导入重新生成的其它面板；不同 ID、内容、描述或目录会正确拒绝。
