# Received variant replay into a review-required package

`python game-ui-harnesses/ui-layer-harness/ui_layer.py finish-variants --selection SELECTION.json --output NEW_DIRECTORY --viewer BUILT_VIEWER` is an optional offline recovery operation. It performs no model or image-generation calls, does not retry a provider request, and leaves the original DAG and all historical review results untouched.

When a complete processed candidate preview already exists, the selection can be discovered in the same command: `finish-variants --snapshot SNAPSHOT --preview PREVIEW --jobs-root JOBS_DIRECTORY --output NEW_DIRECTORY --viewer BUILT_VIEWER`. The program scans direct child job directories for verified received requests, reproduces their sheet cells and allowed deterministic adaptations, then matches each preview source by SHA-256. It writes `NEW_DIRECTORY-selection.json` beside the package and `discovery.json` beside the ZIP. A missing or multiple exact match stops before selection; it never chooses by job age or visual resemblance. `--issues-file FILE.json` may supply a UTF-8 JSON array of known visual differences; otherwise the review note says visual inspection remains pending.

For one complete received job, `finish-variants --received-job JOB --job-digest DIGEST --output NEW_DIRECTORY --viewer BUILT_VIEWER` also creates the candidate preview automatically. It verifies all frozen request inputs and receipts, cuts each sheet into its declared cells, applies only frozen deterministic adaptations, processes the full material set, and then uses the same exact-source discovery and pixel replay. It leaves `NEW_DIRECTORY-sources/`, `NEW_DIRECTORY-preview/`, and `NEW_DIRECTORY-selection.json` as inspectable evidence. Incomplete receipts, a failed sheet cell/alpha/material gate, an ambiguous source or a changed pixel stops packaging. `--issues-file` can carry known visual findings; the package always states that visual review remains pending. This route makes zero model and image-generation calls and never changes a strict DAG failure into success.

Historical frozen sheet prompts are accepted only when their bytes match one of two exact compiler templates: the current wording or its predecessor before the short “small attached props” phrase. Snapshot file hashes, request identity, receipts and all later gates remain required; arbitrary prompt differences still fail.

The explicit `ui_received_variant_selection_v1` input identifies one candidate composite, its original reference, the complete frozen material set and ordered choices of previously received requests. It records each source job/request/material and any selected deterministic adaptation. A selection is a reviewable choice of variants, not a replacement M1/M2/M3 output or a hand-authored package manifest. The candidate and reference have SHA-256 bindings. The selection also contains text/background policies and honest known visual differences.

For every layer, the command verifies the frozen snapshot and preview report, provider submission and receipt, raw PNG hash, sheet cell extraction where applicable, adaptation, and final postprocessed PNG against the preview. The complete layer set and draw order must equal the frozen placements. It then recomposes every replayed PNG and compares every pixel against the candidate composite. Any mismatch stops before package creation; quality gates are unchanged.

On success it writes a portable `ui_layer_composition_v1` ZIP, local Pixi viewer, `review.json` with `status=review-required` and `humanVisualAcceptance=false`, and a private `variant-provenance.json` beside the ZIP. `package-result.json` reports `sourceReceiptReplayPassed=true`, `candidatePreviewMatched=true`, and `originalDagPromoted=false`. No user acceptance is inferred. Source paths, job digests and private lineage remain outside the ZIP.

This proves the deterministic finishing path for a selected set of real receipts. It does not prove that one uninterrupted M1→M2→M3→generation→review DAG selected those variants automatically, or that the generated artwork passes visual review. Existing CLI actions and status semantics remain unchanged. Docker/Web package consumers need no migration; a host that exposes this optional action must provide either a bound selection or the frozen snapshot, complete preview and received job directory, then display the review-required status separately from the original DAG.
