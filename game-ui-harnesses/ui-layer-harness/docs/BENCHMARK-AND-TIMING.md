# 复杂样本离线基准与阶段耗时

这两项能力属于 alpha.6 之后的源码改动，包含在 alpha.7 中，不修改历史标签或旧任务。
`host-run` / `host-*` 仍是正式链路；基准只读任务证据，重放只写新目录。
没有真实生图、模型调用、重试、视觉验收或 Docker 操作。

## 固定样本与四项指标

固定合同是 [`benchmarks/complex-v1.json`](../benchmarks/complex-v1.json)。
原参考图来自仓库本地 `work/ui-reference-generated-20260928-r001`。
合同只保存参考图 SHA-256、尺寸、素材身份、存储几何、声明约束和调用计数；
不包含图片、原始答复、授权、回执、宿主配置或绝对路径。
报告绑定整个合同与证据选择文件的 SHA-256。没有自动更新基线命令；
更换基准应保留 v1，另建版本并审查差异。

| 样本 | 固定证据队列首个任务跑通 | 选择任务的计划/交付素材数 | 基线情况 |
| --- | --- | --- | --- |
| 横屏机库 | 是 | 49 / 49 | 有几何 warning；历史逐请求复审 |
| 横屏烘焙订单 | 否 | 41 / 41 | 首个任务超调用预算；后续独立任务完成 |
| 横屏炼金研究 | 是 | 45 / 45 | 当前一次整图复审；有声明约束残差 |
| 竖屏锦鲤收藏 | 否 | 26 / 26 | 首个任务文字保留冲突；后续独立任务完成 |
| 竖屏极地背包 | 否 | 32 / 18 | 首个任务超预算；选择任务排除了 14 个不确定裁片 |

- **首次跑通**：固定有序队列的第一项是否达到执行终态；后续成功不覆盖首项失败。
  这是所选研究队列的首项，不推断参考图的全部历史尝试，也不是新模型首次生成成功率。
- **素材完整性**：同时比较计划身份与实际 ZIP 图层身份，报告缺失和不确定排除。
  193 个计划身份、179 个已交付身份；4/5 身份齐全。身份齐全不证明素材内容完整。
  `diagnostic_complete`、空复审 findings 或 ZIP 校验通过均不等于素材全部交付。
- **几何一致性**：归一化 `worldShift` 后比较 PNG 存储区域（默认容差 2px），
  并比较已有声明约束、分隔线、色带检查的缺失、失败和残差增加。
  这是存储支持域及声明几何，不能代表语义主体、风格或文字正确。
  已有失败仍披露；新增漂移或测量丢失才记为倒退，不把空集合视为全图通过。
- **调用次数**：分别列出 M1、M2、生图、逐请求复审、主体观察和最终整图复审，
  对固定队列求和后与基线比较。来源是消耗的本地 reservation，不能冒充平台执行或账单计数。
  历史逐素材复审任务保留原策略；新正式链路仍是独立 M1/M2、最多三路持续补位、
  逐素材及主体调用为零、最终整图复审一次。

## 执行离线基准

本地证据选择文件只包含有序任务目录，例如：

```json
{
  "cases": [
    {"id": "orbital-hangar", "attempts": ["work/orbital-first/run"]},
    {"id": "bakery-orders", "attempts": ["work/bakery-first/run", "work/bakery-next/run"]},
    {"id": "alchemy-research", "attempts": ["work/alchemy-first/run"]},
    {"id": "koi-collection", "attempts": ["work/koi-first/run", "work/koi-next/run"]},
    {"id": "arctic-loadout", "attempts": ["work/arctic-first/run", "work/arctic-next/run"]}
  ]
}
```

```sh
python game-ui-harnesses/ui-layer-harness/ui_layer.py benchmark \
  --suite game-ui-harnesses/ui-layer-harness/benchmarks/complex-v1.json \
  --evidence work/benchmark-evidence.json --output work/benchmark-new
```

增加 `--replay-received` 可从兼容的已接收原 PNG 重放诊断归位及打包。
复用 `received_diagnostic_delivery`、`host_layout_registration` 和现有 ZIP 校验；
只复制列明的规划输入、布局 sidecar 和查看器文件，不复制整个生产目录。
不调用 `host-resume`，不复制或重写旧授权、回执、manifest，不重放模型答复。
技术完整性错误停止相应测量，新增倒退使 CLI 退出码为 1。
同一已接收来源的重放另外报告 ZIP、逐层 PNG、回拼预览字节身份；
字节改变会单独记为倒退，不能因素材数和位置相同而漏报像素变化。
任务、参考图、调用文件及最终包仍校验；前后复查原 checkpoint 和文件内容。

旧逐请求复审绑定了原 runtime，无法在新 runtime 下重放。
报告会明确返回 `requires-original-material-review-runtime`，仅做只读基准比较；
完整重放需原不可变安装，不修改指纹、不追加模型复审。
终态失败任务只提供已校验的状态链及 checkpoint 绑定的预约计数，永不重放。
两份超预算历史失败目录的 `.dag/lock` 与 checkpoint 不同：报告保留
`checkpointIntegrityPassed=false`、`deliveryEvidenceUsable=false`，不修复或使用其中媒体。

## 新任务的分阶段耗时

新 `host-run` 自动绑定 `timingPolicy=local-exclusive-phases-v1`。
程序将操作记录写入独立、原子更新的 `timing.json` 指针和 `.journal/timing.json/` 哈希链。
不把计时写入交付包、旧授权或回执。只有绑定新策略的任务才有计时指针例外；
历史任务插入同名文件仍触发 inventory 校验。旧任务保留原安装，不换代码续跑。

```sh
python game-ui-harnesses/ui-layer-harness/ui_layer.py host-timings --run work/new-run
```

报告包含 `planning`、`planning_review`、`image_wait`、`receipt_processing`、
`registration`、`composite_review`、`packaging` 和 `orchestration`。
本地时间来自 `perf_counter`；嵌套阶段按独占时间计数，打包不重复计入归位。
编排与 checkpoint 验证开销单列。只读查询及终态 no-op 不写记录。
操作时间在追加本条计时记录前结束，因此不含该记录自身的锁、校验、写入及释放开销；
它不能替代宿主从进程启动到退出的完整命令耗时。

模型与图片等待从本地预约操作的计时终点至回执/失败命令入口，包含计时记录追加、宿主调度与传输，
不是纯 provider 耗时。并发等待同时报告区间并集和逐请求之和；
墙钟使用并集，不把三路并发的请求耗时相加当总时间。
本地处理还可能与其他在途图片等待重叠，两列不能直接相加当作端到端墙钟。
尚未回执的预约保持 outstanding，墙钟倒退报告 invalid interval，不产生负耗时。
记录写入前进程被强制中断的最后一次操作可能缺失，不能从历史文件时间补造。
旧任务返回 `unavailable-historical-run`，不凭 mtime 推算阶段耗时。

## 可选离线成本细分

在重放命令上增加 `--profile-local`，程序为每份可重放样本写入独立的
`local-profile.json`，并在 `measurement.json` 中绑定报告 SHA-256。
此选项必须和 `--replay-received` 一起使用；只有只读证据对照时不启动 profiler。
正式 `host-*` 链路和未启用选项的基准不安装 profiler，不改变图像编码或 ZIP 方法。

```sh
python game-ui-harnesses/ui-layer-harness/ui_layer.py benchmark \
  --suite game-ui-harnesses/ui-layer-harness/benchmarks/complex-v1.json \
  --evidence work/local-evidence-selection.json \
  --output work/fresh-profile-output --replay-received --profile-local
```

报告分别观测来源准备、诊断渲染、布局归位和末尾产物验证四个顺序操作：
`prepare_received`、`deliver_received`、`register_layout`、`validate_artifacts`。
它们是细分成本的观测范围，与嵌套的 registration/packaging 阶段是两个观察维度，
不能把两组时间相加。报告包含：

- 每个操作的墙钟时间与进程 CPU 时间；进程 CPU 可能包含其他线程，
  墙钟减 CPU 不能直接解释为磁盘等待。
- 按函数**自身耗时**划分且只计一次的 PNG 编码、解码、像素处理、原始像素序列化、
  文件打开/读/写/其他 I/O、文件系统、哈希、CRC、ZIP 压缩/解压/结构处理等类别。
  SHA-256 的文件读取归入 I/O，哈希计算归入 hashing；ZIP 校验的 CRC 单列。
- 最热自身耗时函数和累计耗时函数。累计热点相互嵌套，只用来定位调用范围，不能求和。
- 新输出目录中 ZIP 成员压缩方法的计数。`0` 表示 `ZIP_STORED`，没有 ZIP 压缩计算；
  PNG 内部压缩属于 PNG 编码。内嵌 ZIP 不递归重复计数。

Pillow 的原生 encoder 同时用于 PNG 保存与 `Image.tobytes`，按调用来源拆分，
避免把原始像素序列化全算为 PNG 编码。函数调用次数不是 OS 磁盘操作次数或字节数；
原生编码器内部未暴露的 I/O 可能仍包含在编码耗时中。报告不记录函数参数或绝对路径。
这是含 profiler 开销的诊断数据；普通重放时长另测，不用带 profile 的总时长作性能门槛。
已有 profiler 时直接报 `LOCAL_PROFILE_ALREADY_ACTIVE`，不会覆盖宿主已有观测；
技术错误仍向外传播，不据此创建成功结果或重试。

## 同次任务加载与目录遍历优化

`experimental_executor.load_job` 仍检查配置、纹理、视觉策略、context、合并裁片板、
显式变体、cleanup 和布局绑定。原有 20 个显式错误条件保留。
三类策略要求的相同完整 preflight 合并为末尾一次，在板和变体检查之后重新读取当前
快照字节及目录清单。下次加载重新检查；没有依赖文件长度或 mtime 的信任缓存。
多个同时无效的输入可能改变最先报告的错误，但任何技术完整性失败仍停止。

`validation_scope` 的目录指纹改用 `os.scandir` 复用条目元数据。
每个文件仍读取完整字节并计算 SHA-256，空目录与嵌套名称仍进入清单；
链接、Junction 和特殊条目不产生可复用结果。Python 3.10 的 Windows 分支也拒绝
reparse point。缓存命中前和首次验证后均检查当前指纹，不跨操作继承信任。

炼金快照的 305 项文件/目录清单及内容哈希一致：目录扫描 128 → 64 次，
242 次文件读取全部保留。新增 fixture 检查覆盖三策略共用一次 preflight、
板验证后插入可选输入、相同长度/mtime 篡改、每种策略绑定和板像素篡改；
目录检查覆盖空目录创建/改名/删除与链接/Junction 拒绝复用。

来源检查 `_checked` 累计约 8.08s → 6.10s，目录指纹累计约 5.75s → 3.78s；
这些累计时间相互嵌套。可确定的收益是去除重复验证工作。

本轮打包中位数同时由 4.41s / 2.68s 变为 7.50s / 3.82s，
独立 profile 的总重放时间也由 24.67s 变为 31.21s。
小样本存在明显阶段波动，不能将总时间变化全部归因于此改动，或宣称稳定的端到端加速。
优化 profile 中 264 次 PNG 保存累计 10.82s，对照为 5.76s；
文件打开次数 22,986 → 17,590，累计时间 2.79s → 10.23s。
这些调用分布于归位和打包，说明还需要细分 PNG 编码、文件 I/O、ZIP 压缩与证据哈希，
不能仅凭总时长断定原因。这次波动促成了上节的可选成本报告与三轮复测。
保留全部逐轮测量，不设置时间通过阈值；后续评估同一次加载中的重复 preflight，
仍保留当前字节、inventory 和最终完整包校验。

真实验证另行明确参考图范围、请求数和有限预算，不由基准自动提交生图。

CI 无需本地 work 或私有图片：固定身份/几何数据、真实本地小 PNG 包和正式链路 test doubles
覆盖四项指标的倒退注入、阶段计数、并发等待、终态与篡改边界。
本地完整样本重放属于补充证据，不能替代真实模型质量评估。

## 海洋远征后的离线补充

以下修订包含在 alpha.8 中，不属于已发布 alpha.7 的不可变附件。
新增 [`complex-v2.json`](../benchmarks/complex-v2.json)，保持 v1 文件及其五个案例原值，
追加海洋远征的固定身份、几何及本地预约计数。v2 仍使用原基准命令和合同格式。

海洋队列依次记录首个本地配置失败、修复后规划停在待生图授权、以及复用该快照的生图任务。
正式生图任务实际接收 26 张图（9 张合板、17 张独立图），诊断包包含 60/64 个素材；
四张船员卡因不能证明透明分割而排除。最后的复审连接失败，正式 host-run 保持失败。
用户随后单独授权的一次冻结交付验收不属于这三个 host-run 的预约计数，也不改变失败终态。
两次 `planning_generate` 是本地预约，其中第一次在取得模型答案前失败；不能算作两次模型完成。

基准现在单列 `planning_repair` 和 `planning_rereview`。v1 没有这两个字段，其基线均为零；
新增调用仍会形成倒退。未知模型阶段拒绝测量，避免漏算。失败任务的调用增加也会被报告。

对于**已打包后最终复审失败**的任务，只有 checkpoint 全量 inventory 一致、原整图复审请求、
scope、输入和交付文件摘要全部通过时，才返回 `diagnosticDeliveryEvidenceUsable=true` 并比较素材及几何。
`executionCompleted`、`deliveryEvidenceUsable` 仍为 false，`--replay-received` 也不会重放该失败任务。
报告分别列出选中任务执行完成数量和失败诊断包测量数量；已知失败保持可见，零新增倒退不是执行成功。
若原基线任务已经完成，后来终止仍记录执行倒退，即使已有可测量的诊断包。
只读对照结束也会重新核对源 checkpoint 和实际 inventory，避免测量期间的改动被忽略。

### 滚动协调器的可选计时

已有 Python 接口可以显式启用 `capture_timings=True`：

```python
result = await run_images(run, invoke, capture_timings=True)
timings = result['dispatchTimings']
```

默认不开启，不改变已有结果字段或调度流程。启用后分别记录协调器排队、适配器开始/返回、
已返回结果等待串行回执的时间、回执操作时间，以及前一回执结束到补位适配器开始的延迟。
适配器等待同时给出区间并集和总和，不能与回执排队/处理相加当作墙钟总时间。
这些数据只在返回值中，宿主应保存到受保护 run 目录之外；没有新增持久阶段、授权或调用。
它不能观察原生工具或服务内部的实际开始时间，也不能证明 provider 并发。

海洋远征原始宿主工具事件区间峰值是 1，协调器未完成请求峰值是 3。
原始 26 个工具事件区间合计约 1215.48 秒；正式生图预约到接收等待并集约 2608.42 秒，
其中包含宿主队列、传输及一次本地证据恢复。回执处理约 147.45 秒、归位 19.80 秒、打包 2.66 秒。
这些旧证据不补造新的协调器计时；新字段用于下一次明确授权的真实任务定位排队。

### 合板失败的结构诊断

新的合板 warning 附带 `partitionObservations`：原始检测副本上的四个外缘非零 alpha 数量、
各轴切缝搜索区域、全幅透明行/列数量、最长透明带和原切缝算法错误码。
诊断不选择新的分割策略，不修改像素，不宣称轮廓或来源完整。

海洋船员合板外缘透明，但四卡之间的 alpha=2 及以上辉光没有全幅透明切缝。
因此不能将其解释为仅边缘被裁，也不能通过提高 alpha 阈值或添加外部留白来安全分离。
现有 alpha=0/1 检测准备、原始非零像素保留、严格切缝和不确定素材排除保持不变。
