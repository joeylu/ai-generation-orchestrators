# UI Panel Harness — 原始设计草案

**历史设计快照。** 记录实施前的建议与阶段范围；当前已实现状态和执行证据以
[README](../README.md) 与 [tasks](tasks.md) 为准。本文件中的“尚未实现”描述保留设计当时语境。

## 已确定方向

- 自然语言需求经过组件与资产检索，生成可编辑、可交互的 UI 面板。
- 优先在现有 UI Component Harness 的本地 Pixi/Web 页面预览。
- MUIP 仅作为组件体系和现代 UI 设计的研究参考；建立独立资源与组件配方库。
- Unity 及其他引擎通过各自的导入/导出适配器接入，共享中立面板定义。

下文的首版范围、示例语义和字段分类都是设计建议，不代表已实现能力或用户已确认的业务需求。

## 首个完整样本

输入示例：帮我生成一个设置面板，包含音量设置和音量开关。

首个样本只验证：面板、分组标题、音量设置行、音频开关行、必要文字，以及一套自有现代主题。
设置行与分组是复合组件配方，展开为现有 Panel/Container/Text/Slider/Switch，
不因此新增基础组件类型。外观先采用确定性图形和明确来源的字体、图标。

| 待确认的样本语义 | 建议用于程序夹具的显式约定 |
| --- | --- |
| 音量单位 | UI 状态为整数 0–100，步长 1，显示百分比；宿主负责转换成音频 API 所需单位 |
| 开关含义 | checked=true 表示启用声音，字段命名为 audioEnabled |
| 关闭声音 | 保留音量值；首个夹具允许继续调整音量，不自动重新启用声音 |
| 修改时机 | 控件值变化发出类型化事件；初始化不模拟用户修改 |
| 初始状态 | 来自显式预览数据，不能称为玩家当前设置 |
| 存储与实际声音 | 由宿主接入；预览只验证状态与事件，不隐式保存或修改真实音频 |

这些约定必须随夹具明示。最终用户需求的歧义记录在方案中，不能由编译器静默补齐。
“应用”“取消”“恢复默认”等行为在用户提出或选择相应策略后再纳入该面板。

## 两个主要合同

### PanelSpec：面板创作源（拟定名称）

描述稳定节点 ID、组件配方与槽位、文字与本地化引用、布局约束、主题引用、
状态字段与单位、控件绑定、事件参数，以及目标能力要求。
需求事实、设计系统规则、尚未解决的推断应能区分；未解决的必要语义不能进入成功交付。

首版布局建议限制为固定参考视口内的横向/纵向排列、padding、gap、对齐和显式尺寸约束。
窄屏变体必须另行声明和验证；固定画布缩放不等于响应式重排。
首版绑定保持类型化与有界操作，不接受任意脚本、宿主对象或未经验证的表达式。
动效继续使用独立合同，并明确选择配置，不从“现代风格”自动猜测动效。

### PanelBundle：面板交付包（拟定名称）

复用或包裹现有 UiBundle 的资源封装与校验，不提前声明新的已支持 bundleVersion。
包含原始 PanelSpec、锁定的配方/主题/资源版本及摘要、解析后的组件文档、
宿主接口描述、可选独立动效、能力清单和程序真实生成的验证结果。
预览证据、人工视觉确认、目标引擎验证分别记录，不互相替代。
资源引用采用可移植相对路径；本地解析器负责定位文件，本机路径不进入公共合同。

## 与现有工程的边界

处理链为：需求规划 → 目录候选选择 → PanelSpec → 确定性配方展开与布局 →
现有 TreeIntent/TreePolicy/UiDocument 与资源封装 → Pixi 预览。

- 复用现有[严格组件校验](../../ui-component-harness/docs/tree-contract.md)、资源摘要与路径规则、
  [交互运行时](../../ui-component-harness/docs/runtime.md)、动效合同和浏览器验收。
- 高层约束不直接加入 UiDocument 0.2 的未知字段。布局的计算来源保留在上层，
  不能伪称来自截图测量；兼容层提供现有编译器要求的完整、明确输入。
- 现有 valueTextBindings 可承担支持范围内的数值文字展示；componentLinkages
  是商品列表专用管线，不能据此宣称已存在通用设置绑定。
- 现有 [panel-composition-v1](../../ui-component-harness/docs/panel-composition-v1.md)
  处理 Panel 背景/header/body 外观组合，
  不承担自然语言规划、自动布局、主题或面板业务接口。
- 公共核心保持引擎与模型供应方中立；引用已验证版本，避免复制第二套组件源码。

本目录当前只保存设计。现有仓库的本地 Web 例外仅适用于 ui-component-harness；
未来预览扩展复用该边界，不在本目录新增服务。数据库、部署等不在当前范围。

## 自有目录与检索

目录收录四类内容：设计参数、基础资源、组件配方、面板模式。
每条记录至少标识 ID/版本/摘要、语义与同义词、属性与槽位、状态与事件、
尺寸约束、主题及资源依赖、目标能力、预览和来源。

首版用 JSON/JSONL 与本地文件保存真实记录，建立可重建的内存文本索引。
先按类型、主题、所需状态和本次目标能力过滤，再按语义标签和文本相关度排序。
规划者选择已有 ID，程序验证引用与依赖闭包；不存在的资产必须报告缺项。
核心组件若采用程序化绘制，应作为明确的配方实现登记，不能充当未声明的失败兜底。

用真实需求建立检索评测集。只有评测显示召回不足时，才评估可选 embedding 或重排序；
向量索引不承担资产真实性、版本或能力判断，也不要求立即部署向量数据库。

## 引擎导出

Pixi 是第一目标。第二个验证目标建议为 Unity uGUI：由 Unity 编辑器导入器生成
原生层级、Prefab、必要资源和宿主绑定接口，再按需导出 package。
浏览器生成通用包不等于已经产出经 Unity 验证的 Prefab。

Cocos、Godot、UE 分别设计原生适配器，按具体引擎版本验收。
每个适配器声明能力；不支持的要求必须明确报告，不能把交互控件静默变成图片。
同一面板需要核对文字、几何、裁剪、输入、状态、事件与动效，而不只比较初始截图。

PanelSpec 先作为单一生成源，原生导出是单向编译。宿主手写代码与生成目录分离；
更新使用新产物或明确的覆盖策略。原生编辑反向同步不属于第一阶段。

## 实施顺序与完成标准

| 阶段 | 交付 | 完成标准 |
| --- | --- | --- |
| M0 设计 | 本草案，随后细化最小 schema 与夹具语义 | 区分已有能力、建议与未决项；当前处于本阶段 |
| M1 确定性样本 | 手工编写的 PanelSpec、最小目录、布局/绑定编译与 Pixi 预览 | 相同输入得到相同合同；音量/开关/文字联动符合显式规则；资源完整；保存后恢复一致 |
| M2 自然语言入口 | 需求解析、候选检索、方案修改 | 引用均存在；业务歧义可见；修改一行保留其他节点 ID；错误不保留旧成功结果 |
| M3 第二引擎验证 | 同一设置面板的 Unity 导入器与原生产物 | 指定 Unity 版本导入/重新打开成功；节点、资源、值和事件符合共同测试向量 |
| M4 扩展 | 更多配方、视口、主题及引擎 | 每项能力有独立验证结果，未验证目标继续标为未支持 |

M1 验收至少覆盖：显式初值、范围和步长、关闭后音量保留、禁用态、真实输入、
初始化无用户事件、中文字体与文字溢出、坏引用/摘要拒绝、导出恢复与销毁清理。
声明支持键盘或其他输入方式时，必须有对应真实输入验收。
程序测试采用自有夹具与测试替身，不调用图像/视频生成或私有模型服务。
视觉质量需单独检查，程序夹具通过不能自动标为用户美术验收通过。
